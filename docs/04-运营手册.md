# 04 · 运营手册

> 基准时间：2026-11-04。所有命令都在 `nuxt/` 目录下执行。
> 部署本身见 [`../nuxt/DEPLOY-部署手册.md`](../nuxt/DEPLOY-部署手册.md)，本文只讲**上线之后每天怎么用**。

---

## 0. 每天 / 每周要做的事

| 频率 | 做什么 | 大概耗时 |
|---|---|---|
| 每天 | 看一次审核队列，处理待付款 | 5 分钟 |
| 每天 | 看一次邮箱（有付费单的话） | 2 分钟 |
| 每周一 | 确认周榜归档跑过了（自动） | 1 分钟 |
| 每周 | 备份一次 D1 | 2 分钟 |
| 有单时 | 收款 → 后台确认收款 → 确认条目上线 | 3 分钟 |

**没有必须手动触发的定时任务。** 周榜归档由 Cloudflare Cron 自动跑，广告位到期自动消失。这是重建后和旧站最大的操作差别——旧站要记得跑 `build.py`。

## 1. 打开后台

```bash
# 令牌在你部署时设的 secret 里；忘了就重设一个
npx wrangler secret put NUXT_ADMIN_TOKEN
```

> **令牌存在哪**：`data/admin-token.txt`（权限 600，`.gitignore` 已挡住）。Cloudflare 的 secret 只能写不能读，所以这是唯一能找回它的地方。换机器或换人接手时，把这个文件一起带走。

浏览器打开：

```
https://dirtool.com/admin?token=<你的令牌>
```

**会发生什么**：中间件把令牌写成 `atlas_admin` cookie，然后 **302 到 `/admin`（URL 里的 token 消失）**。这是刻意的——令牌留在地址栏就会进浏览器历史、进任何外链的 Referer、进代理日志。

**打不开 / 404 的三种可能**：

1. `NUXT_ADMIN_TOKEN` 没设或为空 → 后台**整个不存在**（设计如此，不是 bug）。重设 secret 后立即生效，不需要重新部署。
2. 令牌错了 → 和没带令牌一样，都是 404。不会告诉你「错了」。
3. cookie 过期（30 天）→ 重新用带 token 的地址进一次。

后台有四个区块，从上到下就是日常顺序：

```
统计卡片（待审核 / 已上线 / 待付款 / 累计提交）
① 审核队列        免费提交，批准或拒绝
② 待付款          付费档与周广告，确认收款
③ 广告位排期      录入 / 延长 / 立即下架
④ 收录管理        置顶 / 下架
```

## 2. 审核队列

### 2.1 一条记录该看什么

| 看什么 | 判断 |
|---|---|
| 域名是否真的能用 | 点开链接，页面活着、内容跟描述对得上 |
| 一句话是否说清了做什么 | 20–200 字，没有堆关键词 |
| 分类对不对 | 分类错了页面会被归到不相干的地方，宁可拒绝让他重提 |
| 是否是套壳 / 纯 landing page | 没有实际产品的不收 |
| 是否已在精选目录里 | 已在的话提交阶段就会被 `already_listed` 拦掉 |

### 2.2 批准

点「通过」→ 状态变 `approved` → 详情页**立刻**可访问（`/tools/<slug>`），列表页、sitemap 同时出现。

**没有「下次构建生效」这回事。**

### 2.3 拒绝

点「拒绝」→ 弹窗填原因（可选，但**强烈建议填**）→ 状态变 `rejected`，记录**保留**。

保留的原因：一个被拒的域名不能再悄悄重提同一个东西。想让他改完再交，就在理由里写清楚改什么。

理由会原样进拒绝邮件（如果配了邮件密钥）。

### 2.4 为什么付费档在审核队列里点不了「通过」

**因为钱还没到。**

`plan` 是用户选了什么档，`paid_at` 是钱真的到账。付费档未付款时，服务端直接拒绝「通过」（`409 payment_required`）——否则「免费即时上线」就是一次 curl 的距离。

这种记录**永远不会出现在审核队列里**（它在待付款里）。如果你在审核队列看到一条付费档，说明数据是直接写进库的，不是走接口的。

## 3. 收款流程

### 3.1 当前流程（无支付网关）

```
用户选付费档 → 提交 → 记录标为 awaiting_payment
        ↓
用户按定价页的说明付款（微信 / 支付宝 / 转账，人工）
        ↓
你在后台「待付款」看到他，金额就是套餐价
        ↓
点「确认收款」→ 填流水号（可选，建议填）
        ↓
paid_at 写入、状态变 approved、条目当天上线、发收款确认邮件
```

**这一步是整个链路里唯一不能自动化的一环**，也是唯一需要你动手的地方。

### 3.2 套餐对应的权益

价格与权益的唯一来源是 `nuxt/shared/content/pricing.ts`。运营上要记住的只有三件事：

| 档位 | 上线时间 | 链接 | 位置 |
|---|---|---|---|
| Free | 排队，通常 7–14 天，不保证 | nofollow | 目录最后 |
| Standard $19 | 确认收款当天 | 永久 dofollow | 目录优先 |
| Featured $39 | 确认收款当天 | 永久 dofollow | 目录 + 分类置顶 7 天 + 首页卡排期 |
| Pro $69 | 确认收款当天 | 永久 dofollow | 分类置顶 90 天 + 全年 4 次改文案 |

**注意一个实现细节**：提交来的付费收录，`is_paid` 是「付费档且已付款」才算 true，所以它会被排到免费之前。但 `featured_until` 对提交来的条目**是空的**——没有排期，也就没有「7 天后自动回落」。

⇒ **Featured / Pro 卖出去之后，「置顶到哪天」要你在「收录管理」里手动设一次。** 这是目前唯一需要人工补的权益。

### 3.3 广告位订单

广告位是**另一条流**，不走「提交 → 审核」。用户在定价页看到报价，找你下单，你在后台「广告位排期」录入。

`plan=ad` 的提交也会进待付款队列（它走的是同一个表单）。**注意一个副作用**：确认收款后它会和付费收录一样变成一条公开收录，生成 `/tools/<slug>` 页面——因为所有付费档共用同一条上线路径。

如果你不想让这张广告订单出现在目录里：去「收录管理」把它下架（页面变 410，同时从列表和 sitemap 消失），然后正常在「广告位排期」录一条投放。

## 4. 广告位排期

### 4.1 两个位置长什么样

| 位置 | 在哪 | 形态 |
|---|---|---|
| `board` 榜单位 | `/weekly` 第 3 名之后 | 整行：logo + 标题 + 一句话 |
| `sidebar` 右栏位 | 首页与 `/just-added` 的右栏顶部 | 卡片：logo + 一句话 |

### 4.2 报价参考

| 位置 | 单价 | 连投 4 周 |
|---|---|---|
| 榜单位 | $29 / 周 | $99（省 $17） |
| 右栏位 | $19 / 周 | $65（省 $11） |

### 4.3 录入

后台「广告位排期」→ 填位置 / 客户名 / 一句话 / 链接 / 起止日期 / 备注 → 点「排期」。

**保存即生效，不需要部署。** 刷新首页就能看到。

规则（都在服务端校验）：

- 起止日期必须是**真实日期**，`2026-02-31` 会被拒（它会滚到 3 月）
- 结束日期不能早于开始日期
- 链接必须是完整 `http(s)` 地址
- 客户名 2–60 字，一句话 4–90 字
- 同一位置有两条重叠时，**先订的赢**（不会让后订的挤掉正在跑的）

### 4.4 提前下架

列表里点「下架」→ `active = 0`，记录保留。

**不删行的原因**：发票是照这些日期开的，删掉就没得对账。

### 4.5 到期

**不需要做任何事。** 有效期是数据的属性：`end` 是昨天的那条，今天就不渲染了。没有人跑任何任务。

## 5. 置顶与下架

「收录管理」区块，列出精选目录 + 已上线的提交，可搜索。

### 5.1 置顶

点「置顶」→ 可填到期日（不填就是一直到关掉）→ 该条目出现在首页精选与列表最前。

**不动 catalog.json。** 运营置顶是数据库里的一行，重新部署不会丢。

### 5.2 下架

点「下架」→ 详情页**立刻返回 410**，从所有列表、sitemap 里消失。

**410 不是 404**，这是刻意的：404 说「从来没有过」，会让爬虫继续试探；410 说「曾经在，不会回来了」，是下架真正的意思。

### 5.3 恢复

再点一次「下架」按钮（变成「恢复」）→ 页面立刻回来。

## 6. 改价格

改 **`nuxt/shared/content/pricing.ts`** 的两处：

1. `tiers` 数组里的 `price` 字段（页面展示）
2. `comparison` 数组最后一行 `Price`（对照表）

**两处必须一起改**——对照表和卡片不一致是最容易误导买家的错误。

还有第三处容易忘：`nuxt/app/composables/useMySubmissions.ts` 里的 `PLAN_CENTS`（设置页「付款记录」的合计金额）。它按分存储：

```ts
const PLAN_CENTS: Record<string, number> = {
  free: 0, standard: 1900, featured: 3900, pro: 6900, ad: 2900,
}
```

改完 `npm run deploy`（或按部署手册走一遍）。

**不要在页面模板里硬编码金额。**

`nuxt/shared/content/legal.ts`。隐私政策与服务条款都从它渲染。

## 8. 周榜归档（自动）

每周一 03:00 UTC，Cloudflare 触发 Worker，把刚结束的那一周冻进 `week_archive`。

**它解决什么问题**：票是按周存的行，上周的行还在，但「上周的最终名次」需要一个快照。归档存的就是快照——`rank` 也一起存，因为后来的补票不能改写榜单当天说的话。

**确认它跑过了：**

```bash
npx wrangler d1 execute product-atlas --remote \
  --command "SELECT week, COUNT(*) n FROM week_archive GROUP BY week ORDER BY week DESC LIMIT 5"
```

**手动跑一次**（不用等到周一）：

```bash
curl -s -X POST https://dirtool.com/api/admin/archive \
  -H "cookie: atlas_admin=<你的令牌>" \
  -H "content-type: application/json" -d '{}'
# {"ok":true,"week":"2026-W44","rows":18}
```

`rows: 0` 是正常的——那周没人投票。重复跑不会翻倍（先删该周再插）。

## 9. 备份

数据全在 D1，备份就是导出一份 SQL。

```bash
cd nuxt
mkdir -p backups
npx wrangler d1 export product-atlas --remote \
  --output "backups/d1-$(date +%Y%m%d).sql"
```

**怎么算成功**：文件有几 MB 量级，`head -20` 能看到 `CREATE TABLE` 与 `INSERT`。

**恢复**：

```bash
npx wrangler d1 execute product-atlas --remote --file backups/d1-20261104.sql
```

⚠️ 恢复是**覆盖式**的（文件里是 `CREATE TABLE` + `INSERT`），会与现有数据冲突。真要用时先导一份当前的出来，或先 `DROP` 相关表。

**频率**：每周一次足够。写入量极低，一天丢几个小时的数据不致命。

## 10. 故障处理

先看日志，几乎每次都能直接看出原因：

```bash
npx wrangler tail
# 只跟错误
npx wrangler tail --status error
```

### 10.1 站点打不开 / 全站 500

| 检查 | 命令 |
|---|---|
| Worker 在不在 | `npx wrangler deployments list` |
| D1 绑定对不对 | `npx wrangler d1 list`，与 `wrangler.jsonc` 的 `database_id` 比对 |
| 表建了没有 | `npx wrangler d1 execute product-atlas --remote --command "SELECT name FROM sqlite_master WHERE type='table'"` |

**注意**：D1 挂了不会让整站 500。首页、产品库、详情页（精选）都是构建期数据，照常渲染；挂的是提交、投票、最新收录、广告位。如果整站 500，问题在 Worker 本身或绑定，不在数据。

### 10.2 提交报错

接口返回的 `reason` 就是原因，对照 [`03-API接口文档.md`](03-API接口文档.md) §9 的表格。

最常见的两个：

- `duplicate` — 这个域名已经有一条 pending/approved 的提交。去后台看看是不是重复提交。
- `rate_limited` — 同一个 IP 一小时超 5 次。用户在公司/咖啡馆的共享出口后面很容易撞上。让他等一小时，或者你在后台直接帮他建。

### 10.3 用户说收不到邮件

按顺序查：

1. `NUXT_MAIL_API_KEY` 与 `NUXT_MAIL_FROM` 都设了吗？**两个都非空才会发信**，否则静默跳过（这是刻意设计：一封退信不该变成一次失败的提交）。
2. 发件域在 Resend 验证过了吗？
3. 用户提交时填了 `email` 吗？没填就收不到任何通知。
4. `npx wrangler tail` 看有没有 `[mail] delivery failed`。

**注意**：提交接口返回 201 不代表邮件发出去了。邮件是 `waitUntil` 里异步发的，失败只记日志。

### 10.4 广告位不显示

| 可能 | 怎么确认 |
|---|---|
| 日期窗口不对 | 后台列表看「投放期」，`end` 是不是已经过了 |
| 被下架了 | 状态列显示「已下架」 |
| 有另一条更早订的占着这个位 | 同一位置先订的赢，看列表里有没有更早的 active |
| 位置填错 | `slot` 只能是 `board` / `sidebar` |

### 10.5 后台改完没生效

**先硬刷新（Cmd+Shift+R）。** 后台改的是数据库，页面是 SSR 直出，不存在缓存，但浏览器可能缓存了上一份 HTML。

如果硬刷还是旧的：

```bash
curl -s https://dirtool.com/api/overrides
# 看 hidden / pinned 里有没有你刚改的那条
```

API 是新的、页面是旧的 ⇒ 说明页面没读到（极罕见，检查是不是在另一条预览域上）。

### 10.6 回滚代码

```bash
npx wrangler deployments list          # 找到上一个 version id
npx wrangler rollback <deployment-id>
```

**回滚只回代码，不动 D1 数据。** 表结构是加表式的（`IF NOT EXISTS`），旧版本代码不认识新表也不影响运行。

### 10.7 旧 URL 报 404

理论上不会——`server/middleware/01-legacy-urls.ts` 把 `.html` 全 301 了。如果真出现：

```bash
curl -sI https://dirtool.com/pricing.html | head -5
# 期望 301，Location: /pricing
```

404 说明中间件没跑到（检查是不是被别的中间件提前返回了），或者这个 URL 不在规则里。

部署完按这个清单过一遍（命令都在 [`../nuxt/DEPLOY-部署手册.md`](../nuxt/DEPLOY-部署手册.md) 第 9 步）：

## 12. 现在还没有的（运营上要绕开）

| 缺什么 | 影响 | 怎么绕 |
|---|---|---|
| 支付网关 | 收款靠人工 | 定价页写明「确认收款后当天上线」，把预期说清楚 |
| 用户自己改文案 | 已上线的条目用户改不了 | 让他发邮件，你在后台……**目前后台也改不了正文**，只能拒绝让他重提，或直接改 D1（`UPDATE submissions SET short=… WHERE slug=…`） |
| SEO 诊断工具 | `/seo-check` 点了必然报错 | 导航里还在，短期内不要主动推这个页面 |
| DR 数据 | 定价页无法展示权重背书 | 用真实流量截图或第三方数据代替 |

> 第 2 条是运营上最难受的一个洞。真要高频处理，值得排一个「编辑已上线条目」的功能（见 [`06-路线图与待办.md`](06-路线图与待办.md) P1-2）。
