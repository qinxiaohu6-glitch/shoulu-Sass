# 02 · 技术架构

> 基准时间：2026-11-04。代码在 `nuxt/`。上一代 Python 实现已归档到 `legacy/`，见 [`../legacy/README.md`](../legacy/README.md)。

---

## 1. 一句话

**Nuxt 4（Vue 3 + Nitro）跑在 Cloudflare Workers 上，数据在 D1（SQLite），静态内容在构建期打进产物。**

三个选择各自的理由：

| 选择 | 为什么 | 代价 |
|---|---|---|
| Nuxt 4 | 同一份代码同时给出 SSR 页面和 `/api/*`，不需要第二个服务；文件路由让「加一个页面」= 加一个 `.vue` | 框架版本升级要跟 |
| Cloudflare Workers | 无服务器可管：没有 systemd、没有证书续期、没有机器要打补丁；全球边缘 | 运行时不是完整 Node（无 `node:net`，所以邮件走 HTTP API 而不是 SMTP） |
| D1 | 就是 SQLite，本地开发用 `node:sqlite` 跑同一份 `schema.sql`，没有第二套方言 | 单库、写入有上限（对本站量级无影响） |

**旧的 Python 方案被替换的原因**写在 `legacy/README.md`：写入路径依赖一台常开机器、运行时注入靠字符串替换、没有数据库。

## 2. 运行时拓扑

```
                         ┌──────────────────────────────────┐
  浏览器 ──HTTPS──▶      │  Cloudflare 边缘                  │
                         │  · 证书 / CDN                     │
                         │  · Worker 路由（dirtool.com）      │
                         └──────────────┬───────────────────┘
                                        │
                         ┌──────────────▼───────────────────┐
                         │  Worker：.output/server/index.mjs │
                         │  Nitro 运行时                      │
                         │  ┌─────────────────────────────┐  │
                         │  │ middleware（每个请求）        │  │
                         │  │  00-canonical-host           │  │
                         │  │  01-legacy-urls              │  │
                         │  │  admin-token                 │  │
                         │  ├─────────────────────────────┤  │
                         │  │ 页面（SSR）  /  server/api/* │  │
                         │  └──────────────┬──────────────┘  │
                         └─────────────────┼─────────────────┘
                                           │ binding: DB
                                  ┌────────▼────────┐
                                  │  D1（SQLite）    │
                                  │  5 张表          │
                                  └─────────────────┘

  静态资源（CSS/JS/字体/图片）走 binding: ASSETS（.output/public），
  不经过 Nitro，也不消耗 Worker CPU。
```

**构建期就已经确定的东西不打数据库。** 30 个精选产品、8 个分类、15 个标签、5 周历史榜单全部在 `shared/content/catalog.json`，构建时被静态 import 进产物。D1 只装「构建时不可能知道」的四类数据：提交、投票、广告排期、运营覆盖。

这条分界很重要：它意味着**即使 D1 挂了，站点仍然是一个完整可浏览的目录**，只是看不到最新提交、投不了票。`/api/tools` 出错时降级返回空数组（503），页面照常渲染精选目录——这是刻意的降级方向。

## 5. 请求生命周期

### 5.1 三个中间件（按文件名字典序）

```
00-canonical-host.ts   www → apex、http → https、预览域加 noindex
01-legacy-urls.ts      /pricing.html → /pricing（301，保留查询串）
admin-token.ts         /admin?token=… → 种 cookie 并 302 去掉 URL 里的 token
```

**顺序是有意义的。** `00` 必须在 `admin-token` 之前：否则在 `www.dirtool.com/admin?token=…` 上种下的 cookie 属于 `www`，跳到 apex 后就不带过去了。

`00-canonical-host.ts` 的两个细节：

- **GET/HEAD 用 301，其余用 308。** 301 会让客户端把 POST 重发成 GET 并丢掉请求体——一次跨域的表单提交会被静默吞掉。
- **`*.workers.dev` 与预览子域带 `x-robots-tag: noindex, nofollow`。** 它们和 apex 内容一样，不能进搜索结果跟主域抢。

`01-legacy-urls.ts` 的细节：

- **先去 `.html` 后缀，再查 dashboard 映射。** 反过来做会让 `/dashboard.html` 先变成 `/dashboard` 再跳一次——两跳，爬虫会抱怨重定向链。
- `/dashboard(.html)` → `/settings/submissions`（旧仪表盘被设置页取代）。
- `/404.html` → 首页（旧 404 页没有对应新页面）。
- `/index.html` → `/`。

### 5.2 一个 SSR 页面请求

```
1. 中间件（上面三个）
2. app.vue / layouts/default.vue 的 setup
   └─ await ensureSession()  →  内部 GET /api/me（带 cookie，useRequestFetch）
3. page setup
   └─ await useSubmittedTools()  →  GET /api/tools
   └─ useAds() / useBoard() / useOverrides()
4. useSeo() 生成 head：title / description / canonical / hreflang / JSON-LD
5. Nitro 序列化 payload，返回 HTML
```

**会话在 SSR 阶段就解析**（`layouts/default.vue` 里 `await ensureSession()`）。早期版本放在 `onMounted`，结果是登录用户首屏先看到「Sign In」再被替换，每页闪一次错误状态。代价是每个请求多一次 cookie 读 + HMAC 验签，实测 24–40ms 的整页耗时里可以忽略。

### 5.3 一个 API 请求

```
POST /api/submit
  → readBody
  → validate()          字段校验、清洗、分类/标签白名单
  → 域名去重（同域名不得有 pending/approved）
  → IP 哈希配额（每小时 5 / 每天 20）
  → 总量上限 20,000
  → uniqueSlug()        与 catalog 的 slug 也不许撞
  → INSERT
  → sendMail(waitUntil) 不阻塞响应
  → 201 + publicRecord + next: 'review' | 'paid'
```

## 6. 数据模型

全部在 `server/database/schema.sql`，一份文件同时用于 D1 与本地 SQLite。**时间戳统一是整数 Unix 秒。**

### 6.1 `submissions` — 提交队列（26 列）

| 组 | 列 |
|---|---|
| 身份 | `id`（`s_` + 8 hex，随机不复用）、`slug`（唯一，URL 用） |
| 内容 | `url`、`domain`、`name`、`short`、`long_desc`、`category`、`tags`（JSON 数组字符串）、`logo`、`maker` |
| 商务 | `plan`（free/standard/featured/pro/ad）、`slot`（board/sidebar，仅 ad）、`paid_at`、`payment_ref`、`awaiting_payment` |
| 审核 | `status`（pending/approved/rejected）、`reviewed_at`、`reviewer`、`notes` |
| 归属 | `owner_sub`、`owner_email`、`ip_hash`（加盐哈希，不是 IP）、`email`（提交时填的联系地址） |
| 时间 | `created_at`、`updated_at` |

索引：`status`、`domain`、`owner_sub`、`owner_email`、`(ip_hash, created_at)`。

**「是否公开」是一个谓词，不是一列。** 三处（详情页、列表页、sitemap、后台统计）共用同一条规则，SQL 里写成：

```sql
status = 'approved' AND (paid_at IS NOT NULL OR plan NOT IN ('standard','featured','pro','ad'))
```

`plan` 是**意图**，`paid_at` 才是**到账**。付费档在 `paid_at` 为空时永远不渲染公开页——否则「免费即时上线」就是一次 curl 的距离。

### 6.2 `votes` — 每周投票

`PRIMARY KEY (week, slug, voter)`，`week` 形如 `2026-W45`。

**把周写进主键，是「每周一重置」的实现方式**：上周的行留着当历史，本周从空开始，不需要周日半夜跑任何任务。`INSERT OR IGNORE` 处理并发——两个请求撞同一个 `(week, slug, voter)` 只会产生一行，第二个返回 `accepted: false`。

`voter` 是 `sub:<google sub>` 或 `email:<address>`，**从不存原始邮箱到这张表**。

### 6.3 `ads` — 周广告位

`id`、`slot`、`name`、`headline`、`url`、`logo`、`start`、`end`（`YYYY-MM-DD`，两端含）、`active`、`note`、`created_at`、`stopped_at`。

- 有效期是**数据的属性**，不是重建的产物：明天打开页面，昨天到期的广告自然不显示。
- `active` 是运营的急停开关，**与日期分开**——提前下架不能改写开发票时依据的日期。
- 同一位有两个活动广告时，**先订的赢**（`ORDER BY created_at ASC`）。按日期排会让后订的把正在跑的挤掉。
- 日期做真实日期校验：`2026-02-31` 会被 `Date` 滚到 3 月，回读比对不相等就拒。

### 6.4 `tool_overrides` — 运营覆盖

`slug`（主键）、`pin`、`pin_until`、`hidden`、`updated_at`。

- `pin` 让一条精选产品置顶到某天，**不动构建期数据**。
- `hidden` 把它从所有列表里摘掉，详情页回 **410**（不是 404）。404 说「从来没有过」，410 说「曾经有，不会回来了」——运营下架的意思正是后者。
- 两个开关都关掉时**删行**，不留一条全 false 的记录，否则「取消置顶」在表里看起来像没生效。

### 6.5 `week_archive` — 已关闭的周

`PRIMARY KEY (week, slug)`，含 `votes`（最终票数）、`rank`（最终名次）、`created_at`。

`rank` 存下来而不是每次重算：后来的补票不能改写榜单当天说的话。写入是**先删该周再插**，所以重跑不会翻倍。

## 7. 内容层（构建期静态数据）

`shared/content/catalog.json` 是内容真相：30 个产品、8 个分类、15 个标签、5 周历史榜单。

`shared/utils/catalog.ts` 提供所有派生逻辑，页面只调这些函数，不自己算：

## 8. 认证与会话

三个 cookie，都是 HMAC-SHA256 签名的 `base64url(json).signature`（`server/utils/crypto.ts`，用 Web Crypto，因为要在 Workers 上跑）。

| Cookie | 内容 | 有效期 | 谁写 |
|---|---|---|---|
| `atlas_session` | `{sub, email, name, picture, exp}` | 30 天 | OAuth 回调 |
| `atlas_oauth` | `{n: nonce, t: 登录后去向, exp}` | 10 分钟 | `/auth/google/start` |
| `atlas_admin` | 令牌原文（`HttpOnly`） | 30 天 | `/admin?token=…` |

**没有用户表，没有 session 表。** 会话是自包含的：验签 + 查 `exp` 就够，没有一次数据库读。代价是「立即吊销」做不到——所以寿命定在 30 天，且 payload 里只有公开资料。

**登录后去向存在签名 cookie 里，不在 URL 里。** 这样改查询串无法把它变成开放重定向。`safeTarget()` 只放行「以单个 `/` 开头、无 scheme、无反斜杠、无 `..`」的路径。

**`useRuntimeConfig(event)` 必须带 event。** 在 Workers 上不带 event 拿到的是构建期配置，`NUXT_*` 永远不合并进来——一个配置齐全的站点会表现成「`NUXT_ADMIN_TOKEN` 是空字符串，`/admin` 永远 404」，日志里什么都没有。`session.ts` / `admin.ts` / `oauth.ts` 都把 event 设成必填参数，让这种错误变成编译错误而不是线上谜题。

**后台令牌没配置 = 后台不存在。** 不是「默认放行」，是 `isAdmin()` 直接返回 false。

## 9. 安全边界

| 面 | 处理 |
|---|---|
| `/api/admin/*` 未授权 | **404**，不是 403。403 等于确认页面存在并告诉扫描器往哪打 |
| 后台页面 | `/admin` 不在任何导航里；无 cookie 时中间件直接 404 |
| 令牌进 URL | `admin-token.ts` 种完 cookie 立刻 302 到不带 token 的地址，避免它留在历史、Referer、代理日志里 |
| 令牌比较 | `timingSafeEqual`，逐字节 XOR 累积，不提前返回 |
| 提交正文 | `cleanText()` 剥 HTML 标签、折叠空白、**拒绝内嵌链接**（`http://` / `https://` 出现在简介里一律 `no_links`） |
| 提交 URL | 只接受 `http(s)`；`javascript:` / `data:` / `ftp:` 直接拒，不静默升级 |
| IP | 加盐 SHA-256 存前 16 hex，**从不存原始地址**；配额查询只依赖这个哈希 |
| 抓取他人页面（`/api/fetch-meta`） | 当 SSRF 面处理：拒 `localhost` / `*.local` / `*.internal` / `10.x` / `127.x` / `169.254.x`（云元数据）/ `172.16-31.x` / `192.168.x` / `100.64-127.x` / IPv6 环回与链路本地；5 秒超时、256 KB 上限、响应只当文本解析 |
| 广告链接 | `^https?://` 白名单——首页上的 `javascript:` 点击目标是带预算的 XSS |
| 邮件 | 未配置就静默跳过；投递失败只打日志，不让一次退信变成一次失败的提交 |

## 10. 缓存策略

| 资源 | 策略 |
|---|---|
| 静态资源（`ASSETS`） | Cloudflare 默认，内容哈希文件名 |
| `/api/ads`、`/api/board`、`/api/overrides` | `no-store`——广告窗口可能今天午夜结束，缓存副本明早就错 |
| `/api/tools`、`/api/tools/:slug`、`/api/votes` | `no-store`——随时可能有新条目上线或下架 |
| `/api/me`、`/api/my/submissions`、`/api/admin/*` | `no-store` |
| 页面 HTML | SSR 直出，不设 CDN 缓存。理由是页面内容依赖 cookie（顶栏账户菜单）与实时数据 |

**这里刻意没有做 ISR 或缓存层。** 站点量级小、页面 24–40ms，先要正确性。真需要提速时，正确的做法是把 `/api/tools` 的结果放进 `caches.default` 并带短 TTL，而不是缓存整页。

## 11. 国际化

```
defaultLocale: 'en'
strategy: 'prefix_except_default'
detectBrowserLanguage: false
```

- `/` 永远是英文，`/zh` 永远是中文。**不按 `Accept-Language` 跳转**：跳转会让英文首页难以被索引，也会让同一 URL 对不同人显示不同内容。
- 文案在 `i18n/locales/*.json`；页面里仍有大量 `pick(zh, en)` 内联对（`useLang()` 提供），因为那些文案和布局绑在一起。

**⚠️ 内部链接必须走 `localePath()`。** `@nuxtjs/i18n` 在 `prefix_except_default` 下**不会**自动给 `NuxtLink` 加前缀。写成 `to="/tools"` 时，在 `/zh` 页面上会把人送到英文站，而且没有回头路。这个 bug 曾经让中文站整站导航失效（101 个内部链接全部丢前缀）。

**改布局或加链接时的检查方法：**

```bash
# 中文页里应当 0 条不带 /zh 的站内页面链接
curl -s https://dirtool.com/zh | grep -o 'href="/[^"]*"' \
  | grep -v 'href="/zh' \
  | grep -vE 'href="/(_nuxt|assets|favicon\.|apple-touch)' \
  | grep -v 'href="/"' \
  | sort -u
```

三个排除项各有原因：`/_nuxt/` 与 `favicon`/`apple-touch` 是静态资源（不带语言）；`href="/"` 是**语言切换按钮**，它本来就该指向英文首页。剩下的如果还有输出，就是漏了 `localePath()` 的链接。

## 13. 定时任务

`wrangler.jsonc` 里 `triggers.crons: ["0 3 * * 1"]`（每周一 03:00 UTC）。Nitro 把它转成 `cloudflare:scheduled` 钩子，`server/plugins/cron.ts` 接住，把刚结束的那一周冻进 `week_archive`。

- **本地永远不会触发**（`nuxt dev` 没有 Cron），所以同一函数也挂在 `POST /api/admin/archive` 上，可以手动跑。
- **不抛异常**：cron 里 reject 只会留下一条没有上下文的 Worker 错误。它记日志然后返回，下一跳重试——`archiveWeek` 幂等，重试不会翻倍。

## 14. 扩展指南

### 加一个页面

```
app/pages/新路径.vue      → 自动成为路由（中文版是 /zh/新路径）
```

页面里第一件事是 `const localePath = useLocalePath()`，所有 `to` 都写 `:to="localePath('/x')"`。然后 `useSeo({...})` 给 head。

### 加一个接口

```
server/api/foo.get.ts     → GET  /api/foo
server/api/foo.post.ts    → POST /api/foo
```

需要数据库就 `const db = await useDb(event)`；需要登录就 `await readSession(event)`；后台接口第一行 `if (!isAdmin(event)) throw createError({statusCode: 404})`。

### 加一个提交字段

四处都要改，少一处就是线上 500：

1. `server/database/schema.sql` — 加列（`ALTER TABLE` 或改 `CREATE`，线上要单独执行）
2. `server/utils/submissions.ts` — `CleanSubmission` 类型、`validate()` 清洗、`SubmissionRow` 类型、`INSERT` 的列与占位符
3. `publicRecord` / `ownerRecord` / `adminRecord` — 决定这个字段谁能看到
4. `app/pages/submit.vue` 与 `app/pages/settings/submissions.vue` — 表单与展示

### 改价格

只改 `shared/content/pricing.ts`（`tiers` 与 `comparison` 两处必须一起改）。**金额不写在页面模板里。**

注意 `app/composables/useMySubmissions.ts` 里还有一份 `PLAN_CENTS`，用于设置页的付款记录合计——改价时它也要跟着改。

### 加一个分类 / 标签

改 `shared/content/catalog.json` 的 `categories` / `tags` 数组，然后确认 `validate()` 的白名单是**从 catalog 现算的**（是的，`catalogIndex()` 在模块加载时构建），不需要另改代码。

## 16. 关键决策记录

**① 为什么把「是否公开」写成 SQL 片段而不是一列**
`PUBLIC_SQL` 被 sitemap、列表、详情、后台统计共用。如果各自写一遍 `status = 'approved'`，第一次有人忘了 `paid_at` 判断，付费档就会在没收到钱时上线——而这个错误在页面上看起来完全正常。

**② 为什么三种记录形状（`publicRecord` / `ownerRecord` / `adminRecord`）**
`publicRecord` 刻意**不含** `paid_at` / `payment_ref`。这两个字段是关于钱的，只出现在「这一行的所有者」和「站长」两种形状里。分层的目的不是省字段，是让未来某个公开列表**不可能**因为顺手 `...row` 而泄露付款信息——那种错误在索引之后才看得见。

**③ 为什么 `awaiting_payment` 与 `paid_at` 是两件事**
`plan` 是用户选了什么档，`paid_at` 是钱真的到账。`reviewSubmission` 明确拒绝审批「付费档但未付款」的提交（抛 `payment_required`），所以这种行**永远不会进入审核队列**。设置页把它显示成「待付款」而不是「审核中」——否则用户会等一个不可能到来的决定。

**④ 为什么下架用 410 而不是 404**
404 让爬虫继续试探；410 是「曾经在，不会回来」。运营下架一条收录，意思正是后者。

**⑤ 为什么邮件走 HTTP API 而不是 SMTP**
Workers 没有 `node:net`，开不了 SMTP socket。Resend 的 REST 端点是一次 `fetch`。

**⑥ 支付链路（2026-11-08 更新）**
早期版本确实没有支付网关、靠人工确认收款：用户选付费档 → `awaiting_payment` → 站长线下收款 → 后台点「确认收款」→ `paid_at` 写入、状态置 approved。这条链路的每一环都已实测（见 05 文档），并作为兜底保留至今。

**现已接入 Waffo Pancake 生产收款**：服务端 `planAmountCents()` / `adPriceCents()` 算价 → `checkout.createSession()` → `/api/payments/webhook` 验签 → `settleOrder()` 幂等置 paid → Listing `confirmPayment()` 自动发布 / Ad `activateAdBooking()` 自动排期。付款成功即上线，人工按钮只在回调丢失时兜底。详见 `08-在线支付接入.md`。
