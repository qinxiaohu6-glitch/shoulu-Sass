# 08 · 在线支付接入

> 状态：**已接入真实支付（Waffo Pancake，生产已上线）。**
> 本文第 2 节之后描述的是接入前的预留设计，保留作实现参考；**当前运行时行为以本节为准**。

---

## 1. 现在是什么状态（2026-11-08 更新）

```
提交付费档 → 建 payment_order（服务端 planAmountCents() 算价）
  → Waffo checkout → 支付成功
  → /api/payments/webhook 验签 → settleOrder()（WHERE status='pending' 保证幂等）
  → Listing: confirmPayment() 自动发布 / Ad: activateAdBooking() 自动排期
  → 收据邮件发到提交人邮箱
```

**付款成功即自动收录发布，不需要站长确认收款，也不需要人工点按钮。** 免费档仍进人工审核队列（通常 7–14 天，不保证）。

后台的「手动补发 / 确认付款并上线」入口保留为**异常兜底**：仅在回调丢失、支付处理器未启用时由站长手动调用 `confirmPayment()`，正常链路不会用到。人工兜底与 webhook 走同一个函数，所以行为一致。

在生产 secrets `NUXT_PAYMENT_PROVIDER` 等 6 项已配置的情况下，页面、邮件、法务页与 AI 资产里的承诺统一表述为「付款成功后自动收录发布」。

## 2. 已经写好的东西

### 2.1 数据表 `payment_order`

一次付款尝试一行。一条提交可以有多行（卡被拒了再试一次），哪一行成功哪一行上线。

| 字段 | 说明 |
|---|---|
| `id` | 我们自己的订单号 `po_` + 96 位随机，回跳页靠它，换支付平台也不变 |
| `submission_id` | 对应哪条提交 |
| `amount_cents` | 金额（分）。**服务端从定价表读，绝不从请求体读** |
| `provider` / `provider_ref` | 支付平台名 + 平台自己的会话号 |
| `status` | `pending` / `paid` / `failed` / `cancelled` / `refunded` |
| `raw_event` | 回调原文，原样存。有争议时查的是这个，不是我们的摘要 |
| `note` | 失败原因。Stripe 的原话会写在这里（例如 `Invalid API Key provided`） |

唯一索引 `(provider, provider_ref) WHERE provider_ref <> ''`：同一个会话号不可能写两次。

### 2.2 代码位置

| 文件 | 作用 |
|---|---|

### 2.3 前端行为

- 提交成功页：**只有 `ready: true` 才出现「现在付款 $39」按钮**；否则保持原来的人工付款文案。
- 「我的提交」列表：待付款的行多一个「去付款」按钮，同样只在 `ready` 时出现。
  买家关掉标签页之后还能回来付。
- 回跳页：`pending` 时每 3 秒查一次，最多 45 秒；之后提示「还在确认，好了会通知你」。

## 3. 商户号下来之后：五步

### 第 1 步 · 配三个环境变量

在 Cloudflare（或 `.env`）里加：

```
NUXT_PAYMENT_PROVIDER=stripe
NUXT_STRIPE_SECRET_KEY=sk_live_...        # 先用 sk_test_... 测
NUXT_STRIPE_WEBHOOK_SECRET=whsec_...
```

**三个必须同时给。** 只给名字不给密钥，`getPaymentProvider()` 返回 `null`，
站点回到人工收款，不会出现「按钮在、点了报错」。

### 第 2 步 · 在 Stripe 后台加 webhook

- 地址：`https://<你的域名>/api/payments/webhook`
- 订阅事件：
  - `checkout.session.completed`
  - `checkout.session.expired`
  - `checkout.session.async_payment_failed`
  - `charge.refunded`
- 拿到 `whsec_...` 填进第 1 步。

> 只订阅这四个。多订的事件会被忽略并回 200，不会出错，但没必要。

### 第 3 步 · 跑一笔测试付款

用 Stripe 测试卡 `4242 4242 4242 4242`，提交一条 `featured` 档的产品。
预期：

1. 提交成功页出现「现在付款 $39」
2. 点进去是 Stripe 的托管页（卡号不经过我们）
3. 付完跳回 `/payment/return?order=po_...`
4. 页面上几秒内从「正在确认」变成「付款成功」
5. 后台「订单」页出现一行 `paid`，收录列表里这条已经上线

### 第 4 步 · 看后台「订单」页的接入状态

`/admin/orders` 顶部会写：

- `Manual payments` — 没配
- `Half configured` — 配了名字但缺密钥（这一栏就是用来抓这种错）
- `stripe` — 三个都在

### 第 5 步 · 换生产密钥

把 `sk_test_` 换成 `sk_live_`，webhook 换成生产端点的 `whsec_`，再跑一笔小额真实付款。
**换完必须真的付一笔**——签名密钥错了只有真实回调才会暴露。

## 4. 安全上做了什么

| 风险 | 处理 |
|---|---|
| 客户端改价格 | 金额由服务端从 `shared/content/pricing.ts` 读，请求体里只有 `submission_id` |
| 伪造回调 | HMAC-SHA256 验签，`timingSafeEqual` 比较 |
| 重放旧回调 | 时间戳 ±5 分钟，超出直接 400 |
| 同一个回调投两次 | `settleOrder()` 只把 `pending` 改 `paid`，第二次改 0 行，返回 `duplicate: true` |
| 少付钱 | 回调金额 ≠ 订单金额 → 标记 `failed`，**不上线**，写清楚差额 |
| 订单号被猜到 | `po_` + 96 位随机；查状态接口只回订单状态，不回邮箱和地址 |
| 未配置时被扫 | webhook 直接 404，和后台接口一样不暴露存在 |

## 6. 本地验证记录（2026-11-05）

用假密钥 `sk_test_FAKEKEY` + `whsec_testsecret` 在本地跑了一遍完整链路：

| 场景 | 结果 |
|---|---|
| 未配置 | `/api/payments/config` → `ready:false`；checkout → 409 `unconfigured`；webhook → 404 |
| 配了假密钥 | config → `ready:true` |
| checkout（假密钥） | 502，订单行落库为 `failed`，`note` 是 Stripe 原话 `Invalid API Key provided: sk_test_***EKEY` |
| 正确签名的回调 | 200，订单 `paid`，提交 `approved` + `paid_at` + `payment_ref`，详情页立刻 200 |
| 同一回调第二次 | 200 `duplicate:true`，不重复上线 |
| 签名错 / 时间戳过期 | 400 `bad_signature` |
| 金额对不上（付 100 分，订单 3900 分） | 200 `ignored:amount_mismatch`，订单标 `failed`，**没上线** |

> 也就是说：除了 Stripe 自己那一侧的真实付款，其余全部跑通了。
> 真账号下来后要验的只剩「跳过去能付、回来能收到回调」这两下。
