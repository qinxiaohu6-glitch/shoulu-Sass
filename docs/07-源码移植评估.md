## 一、先说最重要的一件事

源码和我们现在跑的，**不是同一套技术栈**，连语言都不同。

| | 源码 `shipany-dir` | 我们 `nuxt/` |
|---|---|---|
| 框架 | **React 19 + TanStack Start**（Vite + Nitro beta） | **Vue 3 + Nuxt 4** |
| 组件写法 | TSX（JSX） | SFC（`.vue`） |
| 路由 | 文件路由（TanStack Router，类型安全） | 文件路由（Nuxt） |
| ORM | **Drizzle**（SQLite / MySQL / Postgres 三方言） | 手写 SQL + D1 |
| 认证 | **better-auth**（邮箱密码 + OAuth + 验证邮件 + 找回密码 + 邀请码） | 自建 HMAC 会话 + Google OAuth |
| i18n | **Paraglide**（编译期生成，1,971 条 × 2 语言） | 手写 `pick('中文', 'English')` |
| UI | **shadcn/ui + Tailwind v4**（29 个基础组件） | 自定义 CSS 6,623 行（原站样式表） |
| 支付 | **Stripe + DodoPayments**（真支付 / 订阅 / 积分） | 人工确认收款 |
| 后台 | 21 个独立页面 + RBAC + MCP Agent | 单页四块 |

**没有一行代码可以直接复制过来。** JSX 不能进 `.vue`，Drizzle 的 schema 不能进 D1 的手写 SQL，Paraglide 的 `m['key']()` 不能进我们的 `pick()`。

## 二、真正值得抄的不是代码，是这六个设计决策

源码的价值在结构，不在实现。以下六点是它比我们成熟的地方：

**1. 外壳统一：240px 左侧栏 + 56px 吸顶头**
所有内页（工具、分类、标签、合集、提交、广告、博客）共用同一个 `DirectorySidebar` + `DirectoryHeader`。左侧栏分两组：浏览（发现 / 工具 / 分类 / 合集 / 标签 / 动态）、更多（博客 / 提交 / 招商）。搜索是 `Cmd+K` 弹层，不占布局。

我们现在是顶部导航条，且导航项散在 `default.vue` 里。

**2. 内容模型：主体表 + 翻译表**
一个工具在 `directory_tool` 里存通用字段（slug、官网、定价、图标、截图、状态、置顶、赞助、来源），文案全部在 `directory_tool_translation`，按 `locale` 一行一份。翻译表字段有 9 个：`name / tagline / introduction / howToUse / features / useCases / faqs / pros / cons`。

我们现在是 `catalog.json` 里 `name_en` / `name_zh` 平铺成两个字段。**这是最关键的一条**——它决定了「一个工具能不能有真正完整的双语长文案」。

**3. 详情页的信息架构**
七个分区，带右侧粘性目录（`StickySectionNav`）：

```
What is {name}?        ← 概览
How to use {name}?     ← 有序步骤
Key features           ← 双列卡片，带 Check 图标
Use cases              ← 双列卡片
Pros & Cons            ← 两列对照
FAQ                    ← 手风琴
Screenshots            ← 截图集
```

我们现在详情页只有「关于 + 相似产品」两块（461 行，大部分是布局）。

**4. 合集（Collections）**
人工编排的专题列表：`directory_collection` + `_translation` + `_collection_tool`（带 sort）。路由 `/collections` 和 `/collections/$slug`。

**我们完全没有这个概念。** 它是 SEO 长尾的主力——一个「Best AI Writing Tools 2026」页面能吃掉一批词，而且不需要新内容，只是重新编排已有工具。

**5. 赞助位分级带库存**
`silver $49 / 12 位`、`gold $149 / 8 位`、`platinum $299 / 4 位`，每档有 `spots` 和 `left`，未付款订单 60 分钟释放库存（`SPONSOR_PENDING_PAYMENT_TTL_MS`）。

我们现在是 `ads` 表 + 后台手工排期，没有库存概念、没有分级、没有自动售罄。

**6. 后台是「表格 + 抽屉」**
21 个页面：工具 / 分类 / 标签 / 合集 / 广告 / 用户 / 订单 / 订阅 / 积分 / 工单 / 文章 / 客座投稿 / 邀请码 / 角色 / 权限 / 设置 / 分析漏斗 / Agent。

我们现在是 `/admin` 一页四块（审核队列、待付款、广告排期、收录管理）。

### 这个差异意味着什么

源码的做法是工具进库 + 后台 CRUD。**这是「其他页面按源码调整」里最硬的一块地基**：详情页那七个分区，如果内容还在 JSON 里，就只能写死在代码里，站长永远改不了。

## 六、视觉：外壳其实已经一致（我最初的判断是错的）

写这份文档时我以为我们是「顶栏 + 单列」，源码是「左栏 + 吸顶头」，需要换壳、会打架。**查代码后发现我们已经是同一套。**

| 维度 | 源码 | 我们 | 差异 |
|---|---|---|---|
| 外壳结构 | `lg:grid-cols-[240px_1fr]` | `.shell{display:flex}` + `.sidebar` = `15.5rem`（248px） | 8px |
| 顶栏 | `h-14` = 56px，`sticky top-0`，`backdrop-blur` | `--header-h: 3.25rem` = 52px，`sticky` | 4px |
| 内容宽 | `max-w-[1320px] px-4 py-6` | `.container{max-width:1320px;padding:24px 16px}` | 0 |
| 首页两栏 | `1fr + 300px` 右栏 | `.home-layout` + `.rail` | 0 |
| 搜索 | `Cmd+K` 弹层 | `SearchDialog` 组件 | 0 |
| 品牌位 | 左栏顶部 logo + 名称 | `.sidebar__brand` logo + 名称 | 0 |
| 招商卡 | 左栏底部 promo | `.sidebar__promo` | 0 |

**结论：外壳不用动。首页保持 `mk-*` 也不会打架——它本来就长在这个外壳里。**

顺带纠正一个认知：`legacy.css` 那 6,542 行不是「旧站遗留的包袱」，它是**这套外壳 + 全部组件的实现**，和源码的 shadcn 体系是两套平行的设计系统。我们选了保留自己的，那新组件就必须用同一套写法（plain CSS + `--background` / `--primary` / `--border` 这些已有令牌），**不能混进 Tailwind utility**——因为 `legacy.css` 是 unlayered 的，优先级高于 Tailwind 的 `@layer utilities`，写上去会被静默吃掉。

所以真正的差距**全在内容层**，不在外壳层：

| 差距 | 具体 |
|---|---|
| 详情页 | 我们 2 个分区 → 源码 7 个 + 粘性目录 + 截图集 |
| 列表页 | 少 `name` 排序、价格/来源筛选 |
| 合集 | 完全没有 |
| 导航 | 少「合集」「博客」两项 |
| 首页 | **不动** |

## 七、三阶段方案

### 阶段 A · 内容层视觉（不碰数据）

**目标**：看起来和源码一致，功能一个不变，零数据风险。**外壳不动。**

1. 重做 `/tools/[slug]`：七个分区（What is / How to use / Key features / Use cases / Pros & Cons / FAQ）+ 右侧粘性目录 + 截图集
   - 内容仍读 `catalog.json`；`features` / `pros` / `cons` / `faq` 现在没有，先按「有则渲染」写，阶段 B 进库后自动出现
2. `/tools` 列表：补 `name` 排序、价格/来源筛选，卡片密度对齐源码
3. 新增 `/collections` + `/collections/[slug]`（先读 JSON 里手写的一份）
4. 左栏导航补「合集」「博客」两项
5. 首页：**一行不改**
6. 文案补全：把内联的 `pick()` 收到一处，为阶段 B 的翻译表做准备

**产出**：视觉与源码一致，站长仍改不了正文。
**风险**：新组件必须用 plain CSS + 已有令牌写，**不能混 Tailwind utility**（`legacy.css` unlayered，会盖掉）。

**产出**：视觉与源码一致，站长仍改不了正文。
**风险**：`legacy.css` 与 Tailwind 类混用。我们现在的 CSS 是 unlayered 的，优先级高于 Tailwind utility——新写的 Tailwind 类会被旧规则盖掉。**必须先解决这个，否则内页会「写什么不生效」。**

### 阶段 B · 内容进库 + 后台 CRUD

1. 新建 6 张表（tool / translation / category / tag / collection + 两张关联）
2. 迁移脚本：`catalog.json` → D1
3. 后台四页：工具（含翻译双栏编辑）、分类、标签、合集
4. 详情页改为读库
5. `/collections/$slug` 上线

**产出**：站长能自己改一切，不再需要部署。
**风险**：迁移期双写。要么一次性切，要么留一个「JSON 兜底」开关。

### 阶段 C · 按需（不建议一次做完）

支付（Stripe/Dodo）、账号密码体系、工单、博客、客座投稿、赞助库存、积分订阅 API Key、RBAC。

这些是 SaaS 模板的通用能力，**目录站不一定需要**。建议等前两阶段上线、有真实用户反馈后再挑。

## 九、执行顺序（按依赖排，不按模块排）

选了「A + B + 四个模块」，总工作量约 25–35 个工作日。顺序必须是下面这样，跳步会返工：

| 序 | 做什么 | 依赖 | 为什么排这里 |
|---|---|---|---|
| 1 | **详情页七分区 + 粘性目录 + 截图集** | 无 | 纯前端，能立刻看到效果，且决定了阶段 B 要建哪些字段 |
| 2 | **6 张表 + `catalog.json` 迁移脚本** | 1 定下的字段 | 页面结构没定就建表，字段一定漏 |
| 3 | **后台四页 CRUD**（工具含翻译双栏） | 2 | 没有后台，进库的内容改不了 |
| 4 | **合集**：表 + 两个页面 + 后台 | 2、3 | 依赖工具进库才能编排 |
| 5 | **工单系统**：2 张表 + 用户页 + 后台页 | 3 的后台框架 | 后台壳有了才不用重写 |
| 6 | **博客**：表 + 列表/详情 + 后台 | 3 | 同上 |
| 7 | **在线支付** | 商户凭据 | 见下方阻塞 |

### 阻塞项：在线支付需要你提供

**2026-11-05 更新**：商户号还在申请，接口已经先预留好了——表、四个路由、
Stripe 实现、后台订单页、前端付款按钮全部写完并在本地跑通（假密钥）。
商户号下来后照 `docs/08-在线支付接入.md` 第 3 节走五步即可，业务代码不用动。

到时候需要的是：

- 选 Stripe 还是 DodoPayments（Stripe 已写好；Dodo 要等官方文档，不凭印象编）
- 商户账号的 **API Key**（先测试环境）
- **Webhook 签名密钥**
- 一次性付款（收录费）即可，订阅暂时不需要

### 第 3 步做了什么

**后台从一页变成五页**：`/admin` 保持原样（审核队列 / 待付款 / 广告排期 / 置顶下架），

否则 `/admin/tools` 会是唯一一扇没锁的门。

**写入路径**（`server/api/admin/directory/*`）：

| 路由 | 作用 |
|---|---|
| `GET /api/admin/directory` | 一次取齐工具 / 分类 / 标签 / 合集，四个页面共用同一个 `useAsyncData` key |
| `POST …/tool` | 整对象写入（不是 patch——patch 分不清「清空」和「没提到」），slug 建后不可改 |
| `POST …/taxonomy` | 分类与标签共用，`kind` 决定写哪张表 |
| `POST …/collection` | 成员按整条序列替换，未知 slug 丢弃并回报 `dropped` |

**删除语义分三种，不是一刀切**：

- 工具：真 `DELETE`（列表和详情都不该再出现）
- 分类：写墓碑 `status='deleted'`——内置目录里还有它，真删会被下一次读取复活
- 标签：内置标签**不允许删**，只允许改名。标签是条目自带的词，删掉行但条目还挂着这个词，
  标签页会出现一个没有名字的标题。接口回 400 并说明原因，比给一个假的成功提示诚实

**内容模型**：`dir_tool_tr.detail` 是 JSON 列，读写整块。后台的表单和页面读的是同一个对象，
省掉六张子表，也省掉「加一个字段要改三处」。

### 分类 / 标签读路径切库（第 3 步的尾巴，已补齐）

后台改完名字，`/categories`、`/tags`、`/tools/[slug]` 的标签徽章、`/weekly` 的分类 chip
原本仍然读构建时的 `catalog.json`——**写进去了，但没人读**。这一轮补上了读路径。

**做法：一次读全，跟着 SSR payload 走**

| 件 | 作用 |
|---|---|
| `GET /api/directory/meta` | 一次返回 `{ categories, tags, collections }`，库优先、JSON 兜底 |
| `app/plugins/directory-meta.server.ts` | 渲染前拉一次，塞进 `useState`，随 payload 下发 |
| `app/composables/useDirectoryMeta.ts` | 同步读，零请求，返回 `categories` / `tags` / `collections` 三个 ref |
| `server/utils/directory.ts` 的 `directoryMeta()` | 计数只算一遍，三张表共用一份 tally |

为什么用插件而不是 `useAsyncData`：这些页面是同步 setup + `computed`，改成 `await`
要动 8 个页面的模板（加载态、`v-if`），而插件在 `renderToString` 之前就跑完了，
页面拿到的就是最终值——**零模板改动，也就零样式风险**。

为什么返回 ref 而不是数组：名字是在 `computed` 里解析的，给死数组会把首次渲染的值冻住。

**改到的 12 个文件**：`ToolCard.vue`、`layouts/default.vue`、`pages/index.vue`、
`tools/index.vue`、`tools/[slug].vue`、`categories/index.vue`、`categories/[slug].vue`、
`tags/index.vue`、`tags/[slug].vue`、`just-added.vue`、`weekly.vue`、`makers/index.vue`、
`makers/[slug].vue`、`submit.vue`。

共享函数加了可选 `list` 参数（`categoryBySlug` / `tagBySlug` / `pillCategories` /
`tagLabel` / `makerCategories`），**默认值仍是 catalog**——服务端那些没有 Nuxt context
的调用点（`makerCategories` 内部、`boardRows` 等）一行没改，行为不变。

**页脚那八条也顺手接上了**。它原本是八个硬编码的 `pick('AI 助手','AI Assistants')`，
既不是 catalog 也不是库：分类一改名，页脚还是旧名；分类一墓碑，页脚就挂一条死链。
现在 slug 列表仍是编辑决定（固定八条），**只把标签换成实时名字**，被删的分类自动消失。
八个名字与硬编码值逐字相同，所以没改名时输出逐字节一致。

**代价**：每个页面渲染多约 7–8 条 D1 查询（分类 2 + 标签 2 + 合集 2 + 计数 2）。
本地实测 `GET /api/directory/meta` 5–10ms。如果之后觉得贵，正确的做法是在 Worker
里给这个接口加一层 `caches.default`，而不是把插件改成懒加载——懒加载会把分类徽章
从首屏 HTML 里拿掉。

## 十二、合集公开页（第 4 步）

源码里 `src/routes/collections/index.tsx` 与 `$slug.tsx` 两个文件，207 + 248 行。
React/shadcn 的写法搬不过来，但**结构与信息层级**照搬：列表是卡片网格，详情是
「面包屑 + 标题 + 计数 / 排序 / 工具网格」。

### 没有新增接口

`GET /api/directory/meta` 上一轮就已经把 `collections`（含成员 slug 数组）一起返回了，
所以两个页面直接读 `useDirectoryMeta()`，**一条新接口都没加**。

成员工具则复用站点自己的工具列表：`orderedTools()`（静态目录）+ `useSubmittedTools()`
（社区提交），和 `/tools`、`/tags` 是同一份数据。这样合集卡片上的 logo 不可能出现
一个「列表页根本没有」的产品。

### 三个关键决定

**1. 顺序是功能，不是默认值**

合集的意思是「你应该先试这五个」。所以详情页默认按编辑排的顺序渲染，排序控件是
**主动离开**这个顺序的方式，而不是默认行为。选项只有三个：精选顺序 / 最新 / 最热
（源码有四个，多一个按名称排序——我们的 `/tools` 没有这个词汇，不引入）。

**2. 草稿 = 404，不是「敬请期待」**

后台可以存草稿。`directoryMeta()` 在服务端就把 `status === 'draft'` 滤掉，所以草稿
合集的详情页和「不存在」返回完全一样的 404，也不会出现在列表页、sitemap 里。
后台接口 `listDirectoryCollections()` 不过滤——否则运营看不见自己的草稿。

**3. 成员解析不到就直接消失**

一个成员可能三种方式失效：slug 从来不存在、被运营下架（`overrides.hidden`）、
是还没上线的提交。三种都解析成 `undefined` 被滤掉，**卡片上的数字和下面的卡片数量
永远一致**——不会出现「写着 6 个，只显示 4 个」。

### 顺手修掉的一个真 bug

`POST /api/admin/directory/collection` 原来用 `directoryToolSlugs(db)` 校验成员，
那个函数返回的是**「`dir_tool` 表里有行的 slug」**。但 `dir_tool` 是覆盖层不是全集：
一个刚部署、还没跑 seeder 的库里，30 个目录工具一个都不在表里，于是**任何合集都存不进
成员**——接口还回 `ok: true`，只是 `dropped` 等于全部。

改成用 `listDirectoryTools(db)`（库 ∪ 目录）判断「这个 slug 是不是一个真实收录」，
语义才是对的。`directoryToolSlugs` 保持原样，它服务的是后台的 `db / catalog` 徽章。

### 页脚、侧栏、sitemap、llms.txt 都接上了

新增页面不接导航等于没做。侧栏「浏览」加一条「合集」（图标 `sparkles`——精灵里没有
layers/video/audio，宁可复用现成的也不画一个风格不一致的），页脚「目录」列同理。
`sitemap.xml` 增加 `/collections` 与每个已发布合集的两种语言版本，`llms.txt` 加一行。

### 本地验证记录（合集）

**排序三态**（用一个故意打乱顺序的合集测，目录里的工具恰好按日期倒序排，用它们测
不出区别）：

| URL | 实际顺序 |
|---|---|
| `/collections/zz-order-test` | consensus → elicit → perplexity（编辑顺序） |
| `?sort=newest` | perplexity(09-17) → elicit(09-16) → consensus(09-14) |
| `?sort=votes` | consensus(188) → perplexity(177) → elicit(75) |

**草稿**：改成 draft → 详情页 404、列表页与 meta 里都没有、后台仍可见（可继续编辑）。

**空合集**：详情页出空态、卡片显示 `0 tools`、图标回落到 `sparkles`、页脚不塌。

**路由**：35 条公开路由全 200（含 `/zh` 镜像）。`/collections/nope` → 404。

**结构化数据**：列表页 `CollectionPage` + 3 条 ItemList；详情页 6 条，`@type` 与
`numberOfItems` 都对得上。canonical 与 hreflang 由 `useSeo` 自动带出，中文页指向
`/zh/collections/...`。

**截图**：浅色 / 深色 / 390px 移动端 / 中文各一轮，无溢出、无重叠、无低对比。

## 十三、工单系统（第 5 步）

源码侧是 `src/modules/tickets/service.ts`（353 行）+ 两套页面（`settings/-tickets-*`、
`admin/-tickets-*`）。React 的 Dialog + DataTable 搬不过来，但**语义照搬**：一张工单
一条线程，状态由「谁最后说话」推导。

### 两张表，没有 join

`ticket` + `ticket_message`。源码的 `ticket_message.user_id` 外键指向 `user` 表，
**我们这个版本没有 user 表**——会话 cookie 就是身份（Google sub + email + name）。
所以把作者身份**抄**到工单行上，而不是 join。

这份拷贝是**快照**，不是缓存，理由写在 schema 注释里：改了 Google 昵称的人不该改写
一封以旧名字归档的对话；注销的 Google 账号也不该让旧工单读不出来。

### 三个状态，只有一个是人定的

| 值 | 含义 | 谁写的 |
|---|---|---|
| `open` | 用户最后说话，球在我们这边 | `addMessage` 按 role 自动 |
| `replied` | 我们最后说话，球在用户那边 | `addMessage` 按 role 自动 |
| `closed` | 有人结束了它 | 人 |

`addMessage` 从写入者的 role 推导前两个，所以**状态不可能和线程里最后一条消息矛盾**。
没有 `assignee`、没有优先级、没有 SLA 字段：一个人答这些，一个没人能改的优先级字段
是写在 schema 里的谎话。

### 关闭是硬的：双方都不能再写

用户回复、管理员回复，在 `closed` 上都返回 409。后台有显式的「重新打开」按钮。
一条规则，两个入口，不会出现「关了还能回」或者「回了其实没关」。
（源码后台是把输入框藏起来，我们的做法更严格，也更少歧义。）

### 附件：链接，不是上传

**这个版本没有对象存储绑定**（没有 R2 bucket），所以截图只能是一个链接。校验沿用
源码的两条：只接受 `/` 开头的站内路径或 `http(s)://`，最多 9 个，每个 ≤2048 字符。
`javascript:` / `data:` 进不来。

页面上写明了「本站不代管图片，请先用图床或云盘生成链接」——与其假装能上传，
不如把限制讲清楚。

图片加载失败时缩略图塌成一个小符号（`TicketAttach.vue`）。链接指向别人家的服务器，
404、防盗链、过期分享都是常态，一排空方框看起来像我们自己渲染坏了。

### 列表与线程是同一页的两个状态

`/settings/tickets` 用 `?id=` 切换。不新开路由的理由：回复通知的邮件要带链接，
`/settings/tickets?id=t_…` 短、后退键正常、不需要第二套页面外壳。
后台 `/admin/tickets` 用左右分栏（和工具 / 分类 / 合集一致），比源码的「表格 + 弹窗」
少一次点击。

### 消息气泡不分左右

同一条消息，在用户页是「我」，在后台页是「对方」。用左右位置编码身份，就有一半场景
是错的。所以**两侧都靠左**，用底色区分：用户是 `--secondary`，客服是 primary 淡色 +
左侧竖线（答案应该被一眼看到）。

### 顺手改的两处

**1. 概览页的「24h 工单支持」卡片是假的。** 原来写着「开启邮件后 24h 内回复」，
而站点当时根本没有工单系统。现在显示「等你查看的回复数」，走
`/api/tickets?status=replied&limit=1` 只取 `total`（服务端是 `COUNT(*)`，不取行）。

**2. 错误文案表加了 5 个工单专用码**，没有另起一张表：`too_long`、`bad_attachments`、
`ticket_closed`、`ticket_not_found`、`ticket_rate_limited`。后两个是「同一种情况、
不同的名词」——`not_found` 的文案写的是「找不到这条提交」，照抄给工单会读着别扭，
但改掉它又会动到已经上线的提交页。

### 邮件

两个，都走已有的 `sendMail`（未配置就是空操作）：

| 触发 | 收件人 | 说明 |
|---|---|---|
| 新建工单 | 站长（`NUXT_MAIL_REPLY_TO`） | 没配就跳过——不能回落到 `mailFrom`，那是自己的 no-reply 发件人，看起来成功、实际进黑洞 |
| 管理员回复 | 工单作者 | **只发「有回复了」，不复制正文**。线程才是记录，邮件里带正文会诱导对方用邮件回，后台就只剩半截对话 |

用户回复**不通知站长**：他下次打开 `/admin/tickets` 就能看到 `待处理` 计数。

### 限流

同一账号 30 秒内只能建一张工单，判定方式是读最新一张的 `created_at`。没有加计数表：
一个正常用户碰不到的限额，不值得为它加一张表。

### 本地验证记录（工单）

| 项 | 结果 |
|---|---|
| 建单 | 201，返回 `id` / `status: open`；`attachments` 原样存下 |

`legacy/audit.py`（479 行）与 `legacy/drcheck.py`（129 行）移植过来，同时把页面里
两个 `<div hidden>` 空占位换成真实渲染。

### 移植了什么，改了什么

| 项 | 旧站（Python） | 现在 | 为什么 |
|---|---|---|---|
| 路由 | `GET /api/audit?url=…&lang=…` | `POST` + JSON body | 网址不再进访问日志与 Referer |
| 抓取 | `urlopen` | `fetch` + AbortController | Workers 没有 urllib |
| SSRF | `socket.getaddrinfo` 查解析结果 | 字面量黑名单 + **重定向后再查一次** | Workers 没有 socket / DNS；出口本身到不了私网 |
| 解析 | `html.parser.HTMLParser` | 自写单遍扫描器 | `HTMLRewriter` 只在 Workers 有，`nuxt dev` 跑在 Node 上没有 |
| 4xx/5xx | 归到 `unreachable` | 单独的 `http_error` + `upstream_status` | 「页面 404」和「页面超时」是两种问题，两种改法 |
| 文件探测 | `ThreadPoolExecutor(3)` | 三个 `fetch` 先发起、再同步解析 | 同样是重叠，只是不用线程 |
| DR 缓存 | `data/dr-cache.json`，24h | **24h 内存 memo**（键 `域名\|版本`，最多 500 条） | Workers 无文件系统；Ahrefs license 禁批量抓取，故不建 D1 表、不做批量查询 |
| 限流 | 进程内 20 次/分 | 进程内 20 次/分（每 isolate） | 不落库——FAQ 承诺「不存进数据库」 |

移植时打分口径**一个字没改**：20 项、5 组、`pass=1 / warn=0.5 / fail=0`、每组
`round(得分 ÷ 项数 × 20)`、A/B/C/D/E @ 90/75/60/40。这种数字会被截图传播，
两版之间变一次，信任就没了。

这条约束在后来加检查项时正面兑现了：**不是偷偷把 84 分改成 71 分，而是给口径编号**。
响应里多一个 `rubric` 字段，检查项一变就 +1；页面把版本印在明细区页脚
（`评分口径 v2 · 共 28 项检查`）。这样一张「84 B」的截图不会跟另一张不同口径的
截图被拿来比——见下一节。

### 一处主动改进：`@graph`

旧版只读 JSON-LD 的顶层 `@type`。但主流框架（含 Nuxt 自己）都发成一个
`{ "@context": …, "@graph": [WebSite, WebPage, Organization] }`，于是旧版对
`nuxt.com` 报「没有 schema 类型」并建议「加 Product 结构化数据」——**它已经有三个**。

现在会跟进 `@graph`（深度上限 3 层，防止恶意文档把解析卡死）。同一个 `nuxt.com`：
旧代码 95 分 + 一条假警报，修好后 100 分（这是口径 1 下的对比；口径 2 下同一个站
是 99 分，因为多了 8 项新检查，两者不可直接比）。

### 页面

`<div class="audit" hidden />` 和 `<div class="dr-result" hidden />` 是**从没接过的空占位**，
只补接口用户仍然看不到任何东西。渲染结构照着旧站 `assets/js/tools.js` 的
`renderAudit()` / `renderDr()` 一比一搬过来，所以 `.audit__*` / `.chk` / `.fix` /
`.g-row` / `.dr-*` 这些类在 `legacy.css` 里**本来就有**，一行新 CSS 都没加。
（移植当时确实一行没加；2026-11-08 的 DR4 改造另加了 `.dr-attribution` 与 `.dr-compare*` 一组样式。）

DR 的「未配置」不是错误态：它会说「DR4 查询还没接通」，并在**本页**说明原因——**不再给任何
外部 checker 链接**，输入、查询、结果、失败态全部留在站内（这是硬规则）。所有状态（成功 /
上游出错 / 未配置 / 域名不合法 / 限流 / 无数据）都返回 200，因为它们是答案不是异常。数据源已
换成 Ahrefs 官方免费 `/v3/public/domain-rating-free`（`version=dr4`），付费 API 与
Open PageRank（PR）兜底已移除；契约见 `docs/03` §39。

### 口径 2：从 20 项加深到 28 项

20 项能查出「有没有 title」，查不出「title 里的 schema 缺不缺必填字段」。补的这
8 项全部来自 claude-seo skill 的评分口径（读它的 `SKILL.md` 与 `references/*.md`
当口径来源，不装运行时依赖）：

| 新 check | 组 | 判什么 | 为什么值得单列 |
|---|---|---|---|
| `ai_crawlers` | ai | robots.txt 有没有挡住 **AI 搜索**爬虫 | 见下 |
| `qa_headings` | ai | 有没有以问句写的 H2/H3 | AI 摘录偏好「问题—答案」结构 |
| `authority` | ai | 组织/作者是否具名、带链接，页面有没有 about/contact | E-E-A-T 里唯一机器可读的一块 |
| `schema_required` | schema | 按 `@type` 查必填字段 | 有标签 ≠ 能出富媒体结果 |
| `schema_deprecated` | schema | 有没有用已弃用类型 | 弃用类型不产生富媒体结果，纯属噪音 |
| `hreflang` | crawl | alternates 有没有 `x-default` / 绝对地址 / 自指 | 多语言站最常见的配错 |
| `img_dims` | content | `width`/`height` 有没有写 | 缺了就是 CLS 抖动的来源 |
| `list_table` | content | 有没有 `ul`/`ol`/`table` | 摘要里的列表结果只从这里来 |

`ai_crawlers` 是这批里最有价值的一条。绝大多数站长挡了 `GPTBot` 就以为挡住了
AI——但 `GPTBot` 只管**训练**，决定「ChatGPT 搜索能不能引用你」的是
`OAI-SearchBot`。两者是不同 UA，规则可以分开写。所以这项只认
`OAI-SearchBot` / `Claude-SearchBot` / `PerplexityBot` 三个搜索爬虫，训练爬虫挡了
不影响判定，命中名字写进 `facts.blocked_ai_crawlers`。

**真实站点跑出来的误报，改的是检查而不是站点。** 这一轮用 nuxt.com、apple.com、
MDN、example.com、wired.com 当对照组，暴露了 4 个误报：

| 误报 | 原因 | 怎么改 |
|---|---|---|
| nuxt.com「没有问句标题」 | 只认 `?` 结尾 | 加 `how/what/why/…` 与 `如何/怎么/为什么/…` 前缀匹配 |
| apple.com `img_dims` 0/47 判 fail | 现代写法用 CSS `aspect-ratio` 预留位置 | 封顶 `warn`，`fix` 文案里说明 CSS 也可以 |
| MDN `authority` 判 fail | 页面有 about/contact，只是没有 JSON-LD 里的具名组织 | 三级降级：组织具名+带链接 → pass；具名或 `meta author` → warn；有 about/contact 链接 → warn |
| apple.com `alt` 9/47 判 fail | 空 `alt` 是装饰图的**正确**写法 | 改成「`alt` 属性存在即可」，空值不算缺 |

另外修了一个从旧站继承下来的 bug：`internal` 数的是 `<link>`（样式表）而不是
`<a href>`。旧版对 nuxt.com 报「132 条内链」，实际全是 CSS。现在只数 `<a href>`，
过滤 `#` / `mailto:` / `tel:` / `javascript:`，同一页面变成 49 条。

| `example.com` | **58 D** | 9 pass / 14 warn / 5 fail |

`wired.com` 这条是特意核过的：判定说「挡了」，就得拿原始 robots.txt 逐行对一遍，
确认不是解析器的锅。这类「工具说你有问题」的结论，比「工具说你好」更容易伤到人。
`tailwindcss.com` 同样核过：`curl` 直接拿 `/robots.txt` 与 `/sitemap.xml` 都是
**404**，所以「未找到」是真话，不是探测失败。

**同一个根因只扣一次分。** `robots.txt` 不存在时，`robots` 已经记 warn；
`ai_crawlers` 这时记 **pass**（没有文件就等于什么都没挡），detail 写「没有 robots.txt，
等于全部放行」。最初写成 warn，等于一个缺失文件扣两处，修一次却只补回一分——
这种不公平比少一个检查更伤信任。只有 robots.txt 返回 200 以外的其它状态
（403 / 5xx / 超时，可能真的挡了但我们读不到）才记 warn。
